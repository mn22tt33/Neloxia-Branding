# QUIZORA

## شكل المشروع

```text
ww/
├── backend/       الخادم ومحركات Python وبيانات التشغيل
│   ├── data/      بنوك البيانات ونتائج التشغيل
│   ├── scripts/   سكربتات التثبيت والتشغيل
│   └── tests/     اختبارات الخادم والمحركات
├── frontend/      صفحة الويب وملفات PWA وأصولها
│   └── assets/    الصور والأيقونات والمكتبات
├── docs/          الشروحات
├── run.sh         مشغّل مختصر متوافق مع الأمر القديم
├── setup.sh       مثبت مختصر متوافق مع الأمر القديم
├── server.py      مدخل Python متوافق مع الأمر القديم
├── README.md      بداية سريعة للمشروع
├── .gitignore     يستبعد ملفات Python المؤقتة
└── Solver_Update.zip
```

## وظيفة المجلدات والملفات

### `backend/`

- `server.py`: خادم HTTP وواجهات `/api/*`؛ يدير المهام والتقدّم والسجلات والتزامن. يمكن تشغيله كـAPI مستقل، أو يقدّم ملفات الواجهة عند وجود مجلد `frontend/` بجواره.
- `spx_solver.py`: محرك SPX، ويقرأ/يحفظ بنوك بيانات المواد.
- `qureo_solver.py`: محرك مسارات Qureo، ويقرأ/يحفظ بنك بياناته.
- `gfq_solver.py`: محرك لعبة الأسهم، ويحفظ نتائج الجولات.
- `__init__.py`: يعرّف مجلد الخادم كحزمة Python.

### `frontend/`

- `index.html`: الواجهة العربية، وتحتوي تنسيقات CSS وكود JavaScript داخل الصفحة.
- `manifest.json`: إعدادات تطبيق الويب القابل للتثبيت.
- `sw.js`: تخزين ملفات الواجهة مؤقتًا؛ لا يخزّن طلبات `/api/`.

### `frontend/assets/`

تضم أصول الواجهة أيقونات التطبيق وشعار `quizora-logo.png`، وصور `qureo_top.png` و`spx_mascot.png`، ومكتبة `three.min.js`. لا تستخدم الواجهة صورًا شخصية.

### `backend/data/`

- `spx_api_bank.json` و`spx_api_bank_subject3.json`: بنكا إجابات SPX للمادتين.
- `answers_archive.json` و`answers_archive_subject3.json`: أرشيفا الإجابات النصية للمادتين.
- `qureo_answers.json`: بنك بيانات Qureo.
- `spx_game_results.json`: نتائج جولات لعبة الأسهم.

قد تحدّث المحركات بعض ملفات JSON أثناء التشغيل؛ احتفظ بنسخة احتياطية ولا تخلط ملفات المادتين.

### `backend/scripts/` و`backend/tests/` و`docs/`

- `backend/scripts/run.sh`: يشغّل الخادم ونفق ngrok بعنوان الـAPI الثابت من Termux.
- `backend/scripts/setup.sh`: يثبّت Python وأداة فك الضغط وPRoot-Distro، ثم يجهّز ngrok داخل Debian على Termux.
- `android/termux-widget/`: سكربتا بدء وإيقاف QUIZORA من مهام Termux:Widget.
- `install_android_widget.sh`: ينسخ اختصاري التشغيل والإيقاف إلى Termux:Widget ويربطهما بمجلد المشروع الحالي.
- `backend/tests/`: اختبارات رجوع لاكتمال الحل والطابور والتزامن؛ تُشغّل من الجذر بـ `python -m unittest discover -s backend/tests -v`.
- `docs/اقرأني_طريقة_التشغيل.txt`: خطوات تشغيل مختصرة للهاتف.
- `docs/README.md`: هذا الشرح.

## التشغيل

### Termux

بعد فك `Solver_Update.zip`، ادخل مجلد المشروع ونفّذ أمر الإعداد مرة واحدة:

```bash
bash setup.sh
```

أضف رمز حساب ngrok على الهاتف مرة واحدة داخل Debian عبر PRoot، واستبدل النص برمزك من لوحة ngrok:

```bash
proot-distro login debian -- ngrok config add-authtoken YOUR_NGROK_AUTHTOKEN
```

لا تشارك الرمز ولا تضفه إلى ملفات المشروع. بعد ذلك شغّل الخادم والنفق معًا:

```bash
bash run.sh
```

يعرض التشغيل رابط الموقع العام `https://quizora.movb.workers.dev`، ويظل يعمل ما دام الهاتف متصلًا بالإنترنت وTermux يعمل في الخلفية. استخدم عنوان `http://localhost:8700` للوصول المحلي فقط.
ملفا الجذر `setup.sh` و`run.sh` مشغّلان مختصران للنسختين داخل `backend/scripts/`. أوقف الخادم والنفق بـ `Ctrl+C`.
لا تشغّل النفق على الكمبيوتر والهاتف في الوقت نفسه؛ العنوان العام الثابت مرتبط باتصال واحد. أوقفه على الجهاز الأول قبل تشغيله على الثاني.

### اختصارات Android للشاشة الرئيسية

1. ثبّت تطبيق Termux:Widget من نفس مصدر تثبيت Termux (مثل F-Droid أو GitHub)، ثم افتحه مرة واحدة.
2. بعد إعداد المشروع ورمز ngrok، نفّذ من مجلد المشروع:

   ```bash
   bash install_android_widget.sh
   ```

3. أضف ويدجت Termux:Widget إلى الشاشة الرئيسية، ثم حدّث قائمة المهام. سيظهر خيارا `Start QUIZORA` و`Stop QUIZORA`.
4. اضغط `Start QUIZORA` لبدء الخادم والنفق، واضغط `Stop QUIZORA` لإيقافهما. يظهر تشغيل المهمة في إشعار Termux.

إذا فككت إصدارًا جديدًا في مجلد مختلف، أوقف QUIZORA ثم نفّذ أمر التثبيت من المجلد الجديد لتحديث مسار الاختصارات. لا تحتاج إلى إعادة تثبيت المتطلبات أو إدخال رمز ngrok. ولتفادي إيقاف Android للخدمة، اسمح لـTermux بالعمل في الخلفية وعطّل تحسين البطارية له.

### الكمبيوتر

من جذر المشروع شغّل `python server.py` أو `python backend/server.py`، ثم افتح الرابط الذي يظهر. التشغيل المحلي يستمع على `127.0.0.1` فقط؛ خدمة Railway تستمع على جميع الواجهات لتكون متاحة عبر المنصة.
فعّل «عرض متصفح الحل» من لوحة الإدارة المحلية (`/admin`) لإظهار متصفح منصة Qureo أو SPX على صفحة المنصة نفسها، دون فتح تبويب متابعة إضافي. وضع اللعبة لا يفتح متصفحًا.

### تشغيل ومشاركة الرابط على Windows

- اعمل حسابًا مجانيًا على ngrok وثبّت البرنامج مرة واحدة: `winget install --id Ngrok.Ngrok --exact`.
- من PowerShell على جهازك، ضيف مفتاح ngrok لحسابك بالأمر `ngrok config add-authtoken <NGROK_AUTHTOKEN>`. ما تشاركش المفتاح أو تحطه في ملفات المشروع.
- هتلاقي عنوانك الثابت في صفحة [Domains](https://dashboard.ngrok.com/domains) بحساب ngrok. الخطة المجانية بتستخدم العنوان اللي ngrok بيخصصه لحسابك؛ ما تختارش عنوانًا تخمينيًا.
- لازم يتضبط العنوان المخصص لك في `frontend/config.js` وفي `frontend/config.js` داخل مستودع الواجهة `mn22tt33/Qry33`، وبعدها انشر التعديل على Cloudflare مرة واحدة.
- بعد الإعداد، انقر مرتين على `START_QUIZORA.bat`. الملف بيشغّل الخادم المحلي وngrok على عنوان الـAPI الثابت نفسه المستخدم من Termux، وبيتأكد إن الواجهة على Workers بتستخدمه.
- رابط الموقع اللي تشاركه هو `https://quizora.movb.workers.dev`، وبيفضل ثابت. انشره في [قناة تيليجرام](https://t.me/sprxui77) أو ابعته مباشرة.
- انقر مرتين على `STOP_QUIZORA.bat` لإيقاف الخادم والنفق. لو الخادم وقف، الموقع بيعرض رسالة إن السيرفر المحلي مش متاح؛ أول ما تشغّله تاني الرابط نفسه بيرجع يشتغل.

عنوان ngrok المجاني المخصص لحسابك بيفضل ثابت بين مرات التشغيل، بعكس Quick Tunnel اللي عنوانه بيتغير. الواجهة نفسها بتتقدم من Cloudflare Workers، وngrok بيستخدم لاتصالات الـAPI بس. لازم جهازك يفضل متصل بالإنترنت ومايدخلش وضع السكون؛ لو قفلته أو وقف الخادم، الـAPI مش هيكون متاح مؤقتًا.

مستودع الواجهة المرتبط بالنشر التلقائي على Cloudflare هو `mn22tt33/Qry33`. لازم يكون `frontend/config.js` المنشور فيه عنوان ngrok الثابت الصحيح قبل مشاركة رابط Workers.

صفحة الحساب هي الصفحة العامة الوحيدة؛ تُحوّل الصفحات المحمية إلى تسجيل الدخول حتى عند تعذّر إعداد Firebase أو PostgreSQL. لا تُتاح الواجهة أو واجهات العمليات دون جلسة صالحة، وتُعزل مهام كل مستخدم عن الآخرين. رابط ngrok يظل عامًا لمن يعرفه، وHTTPS لا يضيف تحكمًا في صلاحية الدخول.

## ملاحظات

- محليًا يبدأ الخادم من المنفذ `8700`؛ وعلى Railway يستمع إلى المنفذ الذي يمرره `PORT`.
- ينفذ الخادم عملية واحدة في كل مرة؛ الطلبات الزائدة تنتظر حسب ترتيب إضافتها. في Railway تُحفظ حالة الطابور والسجلات في PostgreSQL، بينما تبقى ملفات بنوك المحركات ضمن `backend/data/`.
- في التشغيل المحلي دون PostgreSQL، لا يبقى الطابور بعد إيقاف الخادم؛ لكن يُحفظ سجل كامل لكل عملية حل ناجحة في `.local-run/solved_count.json`، متضمنًا الكود والمنصة والمدة ووقت الاكتمال دون كلمة المرور. يعرض `/admin` المحلي جميع العمليات عند الضغط على بطاقة العداد. عند الترقية إلى تنسيق السجل الجديد، يُصفّر العداد القديم مرة واحدة لأن تفاصيل عملياته السابقة غير متاحة.
- تعرض شاشة المراجعة عدد المهام النشطة على الخادم والمهام التي تسبق جلسة المتصفح الحالية؛ يتحدّث الترتيب مع اكتمال كل مهمة. الإيقاف وأرشفة النتائج يقتصران على الجلسة الحالية.
- يؤكد محرك Qureo تسجيل الدخول قبل اختيار المسار. عند رفض المنصة الطلب بـHTTP 403 يوقف المحاولة ويعرض تشخيص الصفحة في السجل؛ راجع مزود الخدمة بدل تكرار الطلب من مسار التفافي.
- تبقى خطوة الاختيار وخياراتها بعد إعادة تحميل الصفحة في التبويب نفسه؛ لا تُحفظ أكواد الحسابات أو كلمات المرور في المتصفح.
- التشغيل المحلي مربوط على `127.0.0.1` فقط؛ للوصول من جهاز آخر استخدم نفق ngrok مع إبقاء لوحة الإدارة محلية.
- محركات الحل تتصل بمنصاتها عند بدء المهمة؛ استخدمها فقط مع حسابات لديك تصريح لاستخدامها.
- لا تُعرض المهمة كناجحة إلا بعد تأكيد اكتمال المنهج؛ عند تعذّر بند بعد المحاولات المحدودة ستظهر رسالة فشل وسطر البند في السجل بدل نجاح جزئي.
- `Solver_Update.zip` حزمة توزيع؛ فكّها أولًا، ولا تشغّل الملفات من داخل الأرشيف.

## النشر على استضافتين منفصلتين

### الخادم على Railway

أنشئ خدمة PostgreSQL وخدمة للخلفية في Railway، ثم اضبط **Root Directory** لخدمة الخلفية على `backend/`. يحتوي هذا المجلد على `Dockerfile` مستقل؛ يبني صورة Playwright المطلوبة للمحركات ويشغّل `server.py`. اضبط Healthcheck Path على `/api/health`. يمرّر Railway متغير `PORT` تلقائيًا، فلا تضفه يدويًا.

تُنشأ جداول الطابور والحسابات تلقائيًا عند بدء الخادم. تُحفظ الطلبات وحالاتها وتقدمها وسجلاتها في PostgreSQL، كما يُحفظ كل نجاح في سجل منفصل مشفر للكود ويتضمن المنصة والمدة ووقت الاكتمال. عند أول تشغيل بهذا التحديث، يُصفّر سجل النجاحات القديم مرة واحدة؛ وبعدها تُحفظ كل عملية نجاح مؤكدة وتبقى بعد تنظيف مهام الطابور. يستخدم عامل التنفيذ قفل PostgreSQL مشتركًا، لذلك لا يعمل أكثر من حساب واحد في الوقت نفسه حتى عند تشغيل أكثر من نسخة للخدمة. بعد إعادة تشغيل الخادم تُستكمل الطلبات التي لم تبدأ، وتُعلّم المهمة التي انقطع الخادم أثناء تنفيذها بالفشل بدل تعليقها.

تستخدم الواجهة معرّفًا للطلبات، وتُقيّد مشاهدة الوظائف وإيقافها وتنظيفها برمز ملكية عشوائي في ملف تعريف ارتباط `HttpOnly`؛ لا يكفي تخمين أو نسخ `client_id` للوصول إلى وظائف متصفح آخر. عند تفعيل Firebase Authentication، ترتبط الملكية بمعرّف الحساب، وتُرفض طلبات الحل دون جلسة صالحة. CORS يسمح فقط للأصول المضبوطة ويُرسل ملفات تعريف الارتباط؛ وليس بديلًا عن المصادقة.

### تسجيل المستخدمين بحساب Google

توفّر `/account.html` تسجيل الدخول إلى الحسابات الموجودة عبر Google أو البريد وكلمة مرور QUIZORA. إنشاء الحساب يبدأ باختيار Google، ثم يطلب الاسم وكلمة مرور (8 أحرف على الأقل) وتأكيدها. يتحقق الخادم من Firebase ID token ومزود Google والبريد الموثّق قبل إنشاء الحساب، ويحفظ كلمة المرور كـPBKDF2 hash فقط. تستخدم الصفحة نافذة اختيار الحساب على سطح المكتب وإعادة التوجيه على الهاتف، ثم ينشئ الخادم جلسة عشوائية محفوظة كتجزئة في PostgreSQL داخل ملف `HttpOnly` و`Secure` عبر HTTPS، بصلاحية 30 يومًا. كلمة مرور QUIZORA مستقلة عن كلمة مرور Google.

لإعداد Firebase وGoogle:

1. في Firebase Console افتح **Authentication → Sign-in method** وفعّل مزوّد **Google**.
2. أضف نطاق الواجهة المنشور، مثل `quizora.movb.workers.dev`، إلى **Authentication → Settings → Authorized domains**. أضف `localhost` فقط للاختبار المحلي.
3. أُضيفت إعدادات تطبيق Firebase العامة إلى `frontend/config.js`. هذه الإعدادات، بما فيها `apiKey`، ليست أسرارًا؛ قيّد مفتاح API بنطاقات الواجهة من Google Cloud Console ولا تستخدمه كوسيلة مصادقة.
4. أضف إلى متغيرات خدمة الخلفية على Railway:

| المتغير | القيمة |
|---|---|
| `FIREBASE_PROJECT_ID` | معرّف مشروع Firebase، مثل `quizora-auth-105be`. |
| `ADMIN_EMAIL` | البريد الموثّق لحساب Google الذي سيحصل على صلاحية المدير. |
| `CORS_ALLOWED_ORIGINS` | أصل الواجهة المنشور بدقة، مثل `https://quizora.movb.workers.dev`. |

أبقِ `DATABASE_URL` و`APP_ENCRYPTION_KEY` مضبوطين أيضًا. أول دخول بالبريد المطابق لـ`ADMIN_EMAIL` يمنحه دور `admin`، وكل الحسابات الأخرى تحصل على دور `user`. الوصول إلى `/admin` وواجهات الإدارة يتطلب اتصالًا محليًا وحساب المدير. للخادم المحلي، أضف `FIREBASE_PROJECT_ID` و`ADMIN_EMAIL` إلى `.env` مع إعدادات قاعدة البيانات. بعد ضبط المتغيرات أعد تشغيل الخلفية وانشر الواجهة. إذا كان المتصفح يمنع ملفات تعريف الارتباط عبر النطاقات، استخدم واجهة وAPI على نطاقين متوافقين أو وكيلًا من نفس أصل الواجهة.

أضف المتغيرات التالية إلى خدمة الخلفية:

| المتغير | القيمة |
|---|---|
| `DATABASE_URL` | مرجع Railway إلى قاعدة البيانات، مثل `${{Postgres.DATABASE_URL}}` (استبدل `Postgres` باسم خدمة قاعدة البيانات لديك). |
| `APP_ENCRYPTION_KEY` | مفتاح Fernet ثابت لتشفير أكواد الحسابات وكلمات المرور المخزنة في الطابور. أنشئه محليًا بالأمر أدناه، ثم احفظه في Railway Variables. |
| `CORS_ALLOWED_ORIGINS` | أصل الواجهة فقط، مثل `https://app.example.com`، من دون مسار أو شرطة أخيرة. للفصل بين أكثر من أصل استخدم فاصلة. |

توليد المفتاح:

```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

للاتصال بقاعدة Railway من خادم محلي، ضع `DATABASE_URL` العام الذي توفره إعدادات **Public Networking / TCP Proxy** و`APP_ENCRYPTION_KEY` نفسه المستخدم مع القاعدة في ملف `.env` بجذر المشروع. يحمّل الخادم هذا الملف تلقائيًا، مع أولوية لمتغيرات البيئة المضبوطة مسبقًا. لا تستخدم عنوان Railway الداخلي خارج Railway، ولا تغيّر مفتاح التشفير بعد بدء تسجيل الطلبات. ملف `.env` مستثنى من Git؛ لا ترفع الأسرار ولا تضعها في الواجهة. بعد انتهاء المهمة يحذف الخادم كلمة المرور المشفرة، ويُبقي سجل الطلب والنتيجة. زر «عملية جديدة» يؤرشف النتائج القديمة من العرض ولا يحذف تاريخها من قاعدة البيانات.

إذا لم يُضبط `DATABASE_URL`، يعمل الخادم محليًا بوضعه الحالي داخل الذاكرة؛ هذا الوضع لا يحفظ الطابور بعد إيقاف الخادم. لا ترفع الخلفية على Railway من دون ربط قاعدة PostgreSQL.

### الواجهة على استضافة مستقلة

ارفع محتويات `frontend/` كاملة، بما فيها `assets/` و`config.js`، إلى استضافة ملفات ثابتة تدعم HTTPS. في `config.js` عيّن عنوان خدمة الخلفية العام، من دون إضافة `/api`:

```js
window.APP_CONFIG.apiBaseUrl = "https://your-backend.up.railway.app";
```

استبدل العنوان بعنوان Railway الفعلي. طلبات الواجهة تضيف `/api/` تلقائيًا. يجب أن يطابق نطاق الواجهة أحد الأصول في `CORS_ALLOWED_ORIGINS`. إذا تُرك الإعداد فارغًا، تستخدم الواجهة نفس أصلها، وهو الإعداد المناسب للتشغيل المحلي.

- **أولى بكالوريا** تعرض JavaScript فقط، بلغة المحتوى المطابقة للمسار.
- **ثانية بكالوريا** تتيح اختيار خدمة واحدة فقط: الثقافة المالية أو Python أو JavaScript.
